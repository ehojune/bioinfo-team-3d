# 패치노트 작성 기준

처음 읽는 사람도 무엇이 달라졌는지 알게 씁니다. 한 항목은 두 설명으로 나눕니다.

| 필드 | 쓸 내용 |
|---|---|
| `summary` | 바뀐 동작이나 막은 문제를 쉬운 한 문장으로 설명 |
| `text` | 도구·함수·검사 결과 등 구체적인 변경과 한계 |

```yaml
summary: 이전 분석 결과를 다시 쓸 때 잘못된 파일이 연결되지 않도록 고쳤습니다.
text: 재사용 전 산출물 식별값을 검사하고 CP1 표시와 실행 판정을 일치시켰다.
```

- `CP1`은 계획 승인, `CP2`는 결과 승인, `receipt`는 재현 검사 기록처럼 먼저 풀어 씁니다.
- “안정성을 강화했다” 대신 어떤 실패를 막았는지 씁니다. 개발 문서만 바꿨다면 그대로 밝힙니다.
- 구현·모의 검사 통과를 실제 요청 성공이나 성능 향상으로 바꾸어 쓰지 않습니다.
- 날짜·해시·PR 링크와 기존 기술 기록은 보존합니다. 옛 항목에 `summary`가 없어도 읽을 수 있습니다.
- 생성된 `README.md`는 직접 고치지 않습니다. 원본은 `entries/*.yaml`입니다.
