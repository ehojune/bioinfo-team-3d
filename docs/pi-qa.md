## 물은 것과 답

### 의미 모델·EDAM·온톨로지·그림자·A/B는 실제 요청 어디에 끼나? (10-02)

| 말 | 뜻 |
|---|---|
| 의미 모델 | 지난 요청 기록을 묶은 지도. 출처 모델은 "이 결과를 누가 만들었고 다시 써도 되나", 객체 뷰는 "지금 누가 무엇을 맡았고 무엇이 승인을 기다리나"에 답한다 |
| 온톨로지·EDAM | 지도에 쓰는 낱말 사전. EDAM은 생물정보학 공용 사전으로 데이터 종류·방법 이름과 "이 방법은 이 종류를 받는다"는 관계표가 있다 |
| 그림자 | 계산해 적기만 한다. 계획·prompt·결과는 꺼 둔 때와 같다 |
| A/B | 연구 요청만 반으로 나눠 한쪽에만 "다시 쓸 만한 지난 결과" 목록을 CSO 계획에 참고로 준다 |
| 판단 창 | 연구 요청 10건이나 3주 가운데 먼저 오는 쪽. 그때 버릴지·둘지·넓힐지 정한다 |

예로 "한국인 1000명 데이터로 IF 2 정도 논문"을 맡기면:
1. CSO가 계획을 세우고 PI가 CP1에서 승인한다. A/B는 계획 직전에 한 번 끼어 지난 결과 목록을 주거나(A) 계산만 한다(B).
2. EDAM은 단계마다 "이 방법이 이 입력을 받나"를 맞음·틀림·모름으로 세기만 하고 막지 않는다.
3. 분석·원고 구간에는 의미 모델이 끼지 않는다. 끝나면 그림자가 이번 결과를 지도에 더한다.

데이터 원본은 어디로도 가지 않습니다. 지도에는 ID·종류·hash·개수만 남고 통제 구역 파일은 hash도 읽지 않습니다.
[답 원문](https://github.com/ehojune/bioinfo-team-3d/issues/298#issuecomment-5953905658) · [설정: 의미 모델 그림자](manual.md#설정-포인트)

### open-science는 배울 점이 있나? Paper2Agent 같은 것인가? (10-02)

- 조사 issue [#316](https://github.com/ehojune/bioinfo-team-3d/issues/316)을 만들었습니다. 대상은 aipoch/open-science(local-first 데스크톱 AI research workbench, Apache-2.0)입니다.
- Paper2Agent와 같은 부류인지와 가져다 쓸 개념·코드·구조가 있는지를 함께 봅니다.
- 지금은 보류입니다. Codex 일일 한도를 시운전과 개발에 먼저 씁니다.

### 언제 직접 써 볼 수 있고, 실사용까지 얼마나 남았나? (10-03, 총괄 정리)

- 직접 시험: 지금 됩니다. 공개 데이터로 시작하면 됩니다.
- 공개 데이터·문헌·작은 분석의 실사용: 거의 왔습니다. PI 시운전에서 막히는 곳을 고치면 됩니다.
- 통제 데이터·HPC 실연구: 아직 멉니다. 근거 계층(#58), 연구 규약 나머지(#90), 클러스터 runner와 실제 HPC 제출이 남았습니다.

이 답 뒤에 PI가 버전 정의(v0.25~v1.25)를 내렸습니다. 지금 위치는 [로드맵](manual.md#로드맵)에 있습니다.
[답 원문](https://github.com/ehojune/bioinfo-team-3d/issues/298#issuecomment-5956890705)

### 같은 계정으로 돌릴 때 개인 파일은 얼마나 막히나? (10-03, ③을 바꾼 뒤 총괄 설명)

- 막힘: 개인 경로를 그대로 읽기, 대소문자·8.3 짧은 이름·링크로 돌아가기, `cat`·`Get-Content` 같은 셸 읽기, `cd` 뒤 상대 경로.
- 못 막음: 직원이 작업 폴더에 스크립트를 써서 실행 중에 경로를 만들어 읽는 경우. 게이트는 명령 글자만 봅니다.
- 그래서 실수와 눈에 띄는 접근은 막지만 작정한 직원까지 막지는 못합니다. 공개 데이터 시험(v0.25)에는 충분하고 통제 데이터(v0.75) 전에는 OS 수준 분리를 다시 정합니다.

[답 원문](https://github.com/ehojune/bioinfo-team-3d/issues/298#issuecomment-5958099270) · [PI 개인 경로](manual.md#pi-개인-경로)

### README가 너무 길다. 읽는 사람별로 나누고 로드맵에도 피드백해 줄 수 있나? (10-03)

- README를 셋으로 나눴습니다: [README](../README.md)(처음 써 보는 사람), [매뉴얼](manual.md)(깊이 보려는 사람), 이 문서(PI). 개발 규칙은 AGENTS.md·HANDOFF.md에 둡니다. 어려운 개념 셋(요청 흐름, 승인 게이트, 연구 lane)에는 그림을 넣었습니다.
- 로드맵 순서(PI 혼자 → 통제 데이터 → 다른 사람 → 논문)는 위험이 커지는 순서라 맞다고 봤습니다. 제안은 셋입니다.
  1. 버전마다 통과 기준을 붙인다. 예: v0.25는 공개 데이터 요청 5건 중 4건 이상이 개발자 손 없이 보고서까지.
  2. v0.75를 나눈다: v0.75는 HPC에서 공개 데이터, v0.9는 통제 데이터.
  3. v1 앞에 "다른 사람이 설치해서 공개 데이터로 한 건"을 둔다.
- 결정 대기: ⑥ 아래 표.
