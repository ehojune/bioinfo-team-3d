## 물은 것과 답

### 의미 모델·EDAM·온톨로지·그림자·A/B는 실제 요청 어디에 끼나? (10-02)

| 말 | 뜻 |
|---|---|
| 의미 모델 | 지난 요청 기록을 묶은 지도. 출처 모델은 "이 결과를 누가 만들었고 다시 써도 되나", 객체 뷰는 "지금 누가 무엇을 맡았고 무엇이 승인을 기다리나"에 답한다 |
| 온톨로지·EDAM | 지도에 쓰는 낱말 사전. EDAM은 생물정보학 공용 사전으로 데이터 종류·방법 이름과 "이 방법은 이 종류를 받는다"는 관계표가 있다 |
| 그림자 | 계산해 적기만 한다. 계획·prompt·결과는 꺼 둔 때와 같다 |
| A/B | 연구 요청만 반으로 나눠 한쪽에만 "다시 쓸 만한 지난 결과" 목록을 CSO 계획에 참고로 준다 |
| 판단 창 | 연구 요청 10건이나 3주 가운데 먼저 오는 쪽. 그때 버릴지·둘지·넓힐지 정한다 |

예로 "한국인 1000명 데이터로 IF 2 정도 논문"을 맡기면:
1. CSO가 계획을 세우고 PI가 CP1에서 승인한다. A/B는 계획 직전에 한 번 끼어 지난 결과 목록을 주거나(A) 계산만 한다(B).
2. EDAM은 단계마다 "이 방법이 이 입력을 받나"를 맞음·틀림·모름으로 세기만 하고 막지 않는다.
3. 분석·원고 구간에는 의미 모델이 끼지 않는다. 끝나면 그림자가 이번 결과를 지도에 더한다.

데이터 원본은 어디로도 가지 않습니다. 지도에는 ID·종류·hash·개수만 남고 통제 구역 파일은 hash도 읽지 않습니다.

### 같은 계정으로 돌릴 때 개인 파일은 얼마나 막히나? (10-03, ③을 바꾼 뒤 총괄 설명)

- 아래는 Claude 직원 기준입니다. Windows elevated sandbox의 Codex 직원은 sandbox 읽기 거부와 지침 두 겹을 받습니다([매뉴얼 PI 개인 경로](manual.md#pi-개인-경로)). 셸 명령을 가로채는 게이트는 Claude 직원에게만 있습니다.

- 못 막음: 직원이 작업 폴더에 스크립트를 써서 실행 중에 경로를 만들어 읽는 경우. 게이트는 명령 글자만 봅니다.
- 그래서 실수와 눈에 띄는 접근은 막지만 작정한 직원까지 막지는 못합니다. 공개 데이터 시험(v0.25)에는 충분하고 통제 데이터(v0.9) 전에는 OS 수준 분리를 다시 정합니다.

### 요청이 오면 문헌조사를 하나? 원 연구 Methods를 따라 하나? (10-04)

- 한다. 계획 전에 문헌 담당(lit_scout)이 비서실장 브리핑과 나란히 같은 assay·질문 유형의 최근 논문·리뷰 2–4편을 보고, 필수·권장 분석을 뽑습니다. 필수 항목은 계획이 단계나 가정으로 답해야 하는 점검표가 됩니다([PR #395](https://github.com/ehojune/bioinfo-team-3d/pull/395)).
- 원 연구 Methods는 참고만 합니다. 같은 데이터로 다른 갈래의 분석을 할 수 있으므로 거기에 매이지 않습니다(PI 지시 10-05).
- 갈래별 점검표는 topic마다 있습니다. 17개 topic을 더한 안은 [PR #402](https://github.com/ehojune/bioinfo-team-3d/pull/402)로 병합됐고, 지금 topic은 43개입니다.

### Claude 직원 로그인이 만료되면 어떻게 되나? (10-05)

- 요청은 실패하지 않고 `waiting_login`으로 멈춥니다. 같은 엔진을 쓰는 요청은 대기를 함께 쓰고, 600초마다 다시 시도하며 24시간 뒤 실패합니다([PR #398](https://github.com/ehojune/bioinfo-team-3d/pull/398)).
- 웹 카드에 직원 폴더용 로그인 명령이 뜹니다. 그 명령으로 로그인하고 **로그인했어요 · 다시 시도**를 누르면 바로 이어 갑니다.

### 카드에 바로 답하지 못하면 요청이 실패하나? (10-08)

- 실패하지 않습니다. 확인 질문·직원 질문·예산·범위·CP1·CP2·이어 가기·재개 카드는 7일 동안 기다리고, 그동안 요청은 `waiting_pi`(PI 결정 대기)로 멈춰 있습니다. 돌아와서 카드에 답하면 이어 갑니다.
- 7일이 지나면 요청은 `*_timed_out`(예: `evidence_timed_out`)으로 끝납니다. 거절과 다른 기록이라 보고서와 감사에서 구분됩니다. 기한은 `policy.approvals.pi_decision_timeout_s`로 바꿉니다.
- 도구 권한 같은 gate 카드는 그대로 `policy.approvals.timeout_s`(1시간)가 지나면 닫힙니다. 그 단계만 거절로 처리됩니다.

### CP2에서 근거가 부족하면 어떻게 고치게 하나? (10-08)

- **수정 요청**을 누르고 메모에 고칠 점을 적습니다(메모 없이는 보내지 않습니다). CSO가 그 메모로 새 계획을 세우고, 새 CP1 카드에 재사용할 단계와 다시 돌 단계가 보입니다. 승인하면 바뀐 단계와 그 아래 단계만 다시 돕니다.
- 새 CP1을 거절하면 요청은 처음 결과를 그대로 둔 채 `evidence_revision_requested`로 끝납니다.
- 한 요청에서 이어 가기는 리뷰 revise와 합쳐 2번까지입니다(`research.revise_continuations`). 다 썼으면 버튼이 `수정 요청(요청 끝남)`으로 바뀌고 누르면 요청이 끝납니다.

### CP1 계획이 마음에 안 들면? (10-09)

- CP1 카드에서 **수정 요청**을 누르고 메모에 고칠 점을 적습니다(메모 없이는 보내지 않습니다). 지금 요청은 단계를 돌리지 않고 `plan_revision_requested`로 끝나고, 같은 요청 문장·참고 자료·확인 질문 답에 메모를 붙인 **새 요청**이 바로 시작됩니다. 새 요청이 계획을 다시 세워 새 CP1을 띄웁니다.
- 거절은 지금처럼 요청을 끝내기만 합니다.
- 이어 가기 차수의 CP1(리뷰 revise·CP2 수정 요청 뒤)에는 수정 요청이 없습니다. 이전 차수 결과를 이어 쓰는 계획이라 새 요청으로 옮길 수 없어서입니다.
