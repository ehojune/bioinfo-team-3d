## Installation and first setup


**Process boundary (#666):** It is off by default and refuses requests through the embedding Python API as unsupported. Actual OS protection and authenticated cleanup remain unverified.

**VM preparation draft (#666, PR #1267 under review; draft/hold):** Following the [Hyper-V installation and cleanup guide](../reference/sandbox-666-vm-install.md) (Korean), the user manually runs `Inspect` → `EnableFeature` → any required manual reboot → `Provision` in an elevated Windows PowerShell 5.1 session. There is no automatic elevation, reboot or VM start; the prepared VM remains powered OFF with zero NICs.

`RemoveVM` deletes VM configuration and checkpoints, requiring a prior export/backup, the exact VmId and `-ConfirmConfigurationRemoval` (VHD, ISO and state remain). Actual installation, guest setup, privilege separation, OS protection and termination/cleanup are **UNVERIFIED**; isolation from the same administrator account is **UNSUPPORTED**. The feature stays off by default, disconnected from the ordinary CLI, and #666 remains OPEN.

Prerequisites: Python ≥ 3.10, Git, and the staff CLIs you configure installed and logged in. CLIs installed through npm also need Node.js.

```bash
.\labhq init
.\labhq -c config\labhq.yaml doctor
```

On POSIX use `./labhq.sh init` and `./labhq.sh -c config/labhq.yaml doctor`.

On Windows, a Codex step with ancestor artifacts denies reads from other work folders present at startup. Codex work folders being prepared or run by the same runner, and folders created later, are excluded from this protection. When Codex staff runs overlap, sibling-folder read denial is not guaranteed to last throughout the run (#1413).

`labhq init` copies the example config, generates a random gateway token, and asks for the HPC and bioinfo-agent paths.
New configs enable `research.enabled`, `research.evidence_checkpoint`, the `bulk_tumor_normal@3` and `single_cell_de@3` packs, and `plan.declare_output_types: true` (#613). Paper2Agent hiring defaults to off (`recruit.enabled: false`, #1336). Live semantic devices, actions, A/B and new device reports have been removed; legacy `semantics` and `research.semantic_report` keys are accepted without execution. Vocabulary, EDAM and input-fit checks remain. `REFERENCE_BEHAVIOUR` in `labhq/init_defaults.py` defines these defaults, checked against the example config and `init` by `tests/test_init_defaults.py`. Personal tokens, paths and names are excluded. `pipeline_pr` consent, `dev_log.repo` and `BIOINFO_AGENT_DIR` are requested or discovered. Existing configs are not migrated automatically.
The bioinfo-agent folder is searched in this order: `--bioinfo-agent <folder>`, an existing `BIOINFO_AGENT_DIR`, common locations such as `D:/bioinfo-agent` and `~/bioinfo-agent`, then `/mnt/d/bioinfo-agent` under WSL. If none is found, init asks (it does not ask with `--yes`); if still unknown, it prints "bioinfo-agent not connected — …" and writes the config without the link. A path found or given is stored as an absolute path even if it was relative (a staff task reads relative paths against its own work folder, which would break the link). The `bioinfo-agent` row of `doctor` warns about whether it is connected, and also warns about a config that has a relative path.
`dev_log.repo` (the private repository for the development log) is asked once by `init` as owner/name; Enter leaves it empty. When empty, the log stays on this PC only and the `dev log` row of `doctor` explains how to set it.
For a new config, init also asks about consent to public PR contributions of pipeline code. Only `y` (case-insensitive) consents; Enter, `--yes` or any other answer leaves it off.
If there is no AlphaGenome API key yet, init asks once at the end. Enter skips it; key storage is described in [Public-resource lookup tools](09-staff-tools.en.md#public-resource-lookup-tools).

init also asks for a GitHub token once (optional, #687). It is used to organize request results into a GitHub repository and announce them as issues. Before asking, init shows the permissions needed. A fine-grained token needs Repository creation (or Administration write), Contents write and Issues write, with Repository access set to All repositories. A classic token needs the `repo` scope. If you press Enter to skip, results are stored locally only; later you can rerun `labhq init` or set the `GITHUB_TOKEN` environment variable. If a token is already stored, init asks whether to take a new one. Replace an expired, revoked or re-scoped token here; Enter keeps it. A pasted token is stored only in `github.token_file` (default `~/.labhq/secrets-github/github_token`), readable only by this account like the AlphaGenome key, and never appears in the config file, on screen or in logs. An environment variable takes precedence. Only the gateway process reads the file, at startup; it is not passed to staff, runner or MCP processes. For staff this file is a private path and reads are blocked. Staff CLIs do not use the development GitHub App bot identity, and the user's own GitHub login stored on this PC is separate from it. The doctor that follows checks the permissions (see [Where results are saved](12-github-reports.en.md#where-results-are-saved) below).
init also asks about institutional literature access (optional, #826). It asks for your institution, the official HTTPS proxy prefix your library gives (of the form `https://…login?url=`), the literature services you use, and a contact email for Unpaywall; press Enter to skip any you do not know or want to do later. Do not paste an address from the address bar after logging in. A new config keeps only the proxy (`literature.institution_proxy`) and the email (`annot.unpaywall_email`) and leaves the institution session off. Turn it on yourself after checking the institution's and publishers' terms. An existing config file is not changed; init only tells you which settings to fill in. It does not ask for passwords, cookies or API keys, and does not connect. There is no dedicated automatic connection for Web of Science Research Assistant or Nexus Connect yet. Address formats received and what was verified: [reference](../reference/institution-literature-826.md).
`python scripts/clean_install_check.py` checks init → doctor → mock request → request bundle → verify → down in a fresh clone and venv under a temporary HOME, then by default deletes the temporary folder. To keep the installation and the separated stdout/stderr logs, add `--work-dir <new-empty-folder>`; to choose the PASS/FAIL/SKIP JSON path, add `--receipt <local-receipt.json>`. The installation, logs and receipt contain personal paths and are local-only evidence; do not push them to a public repository ([details](../reference/clean-install-922.md)). It does not log in to a real staff CLI or call a model. The check is isolated from the shell that started it, so the variables Git Bash exports (`MSYSTEM`, `MSYS*`, `MINGW*`, `EXEPATH`, `ORIGINAL_*`) are not passed on: with them set, the `mingw64` `git.exe` dies in the fresh-clone step. Only the fresh-clone step has been checked from Git Bash; the whole run through installation and the mock request has not been compared across shells.

**Running the research mode to the end with the mock engine.** Under the default config `labhq init` writes (research on), with `runner.force_engine: mock` the CSO returns a plan that passes the research contract, and the request goes plan → CP1 → steps → CP2 → review → report and ends `done`. Put `[multistep]` in the request text for a two-step plan where s2 depends on s1, or `[branched]` for a branched plan with two branches (b1, b2) and a synthesis step s3 that reads both. Without a token the plan has one step. `[step-fail]` fails s2 of a multistep plan and `[branch-fail]` fails s2, the second branch, of a branched plan. The failure stays in the report limits and the CP2 warning, while the other branch and the synthesis step still run. `[all-branch-fail]` fails both branches of a branched plan: the synthesis step is skipped and the request ends `failed` (outcome `research_failed`) without CP2. In a team plan outside the research mode (`work_kind: simple`), `[step-fail]` fails the third step (bioinfo-agent); the later steps are skipped and, after one replan, the whole request ends `failed`. Each step has one worker write one output file (`outputs/result<number>.tsv`); topics where a domain pack applies, and a branch that fails, are not imitated. The tests are in `tests/test_e2e_mock.py`.
To run several labs on one PC, run `labhq init --instance <name>` and then add the same
`--instance <name>` to every command. Config, state, runs, talent, ports and tokens are separated per instance.
Engine logins and usage limits are shared by all instances.
The scheduler is detected through `qsub`/`qstat` (SGE, PBS) and `sbatch`/`sinfo` (Slurm); if the type cannot be narrowed to one, init asks (it stops with `--yes`).
If a scheduler tool exists, init runs the HPC consultation (#119). It collects queues, PEs, memory resources and the PBS flavor with read-only queries (SGE `qconf -sql`, `-spl`, `-sp`, `-sc`; PBS `qstat -Q`, `qstat -B -f`, `pbsnodes -a`; Slurm `sinfo`), writes a draft `hpc:` block into the config and shows it.
After saving the config, init shows the submit command for a `sleep 1` test job (1 core, 5 minutes), submits it once only if the PI answers `y`, and tracks it to the end. With `--yes` or `--dry-run` it does not ask, and inside a controlled zone it does not submit.
With no cluster, `scheduler: none`; heavy steps run only through the local CLI, and the CSO says in the plan which steps cannot. The consultation does not decide `ssh_host` or the data-account switch (`submit_prefix`) ([Configuration reference](15-config.en.md#configuration-reference)).
When you pick SGE, PBS or Slurm, init asks for **per-request and per-day** HPC login limits, because an ssh connection can be recorded as a login by the site's IT team. Each institution differs, so there is no default: empty means no limit (and an empty answer is final), and it is asked only with a person at the terminal (`--yes` and pipes do not ask and leave it undecided). At a limit labhq opens no new connection and stops polling that request's jobs. See "HPC login limits and counter" in the [config chapter](15-config.en.md) for the behavior. An existing config that is still undecided (made before #1295, or with `--yes` or a pipe) is asked once on a re-run at the terminal, and only those three keys are saved (other lines and comments stay).

**HPC site profile** (#1300): how a cluster is reached differs by institution (direct ssh, a gateway tunnel, a VPN, a file-transfer window). So when you pick SGE, PBS or Slurm, init asks "Write down how this cluster is reached as a site profile?", and on `y` asks for a profile name and then, in turn: the access method (`ssh`, `gateway_tunnel`, `vpn`, `other`), the connect command (words separated by spaces), how to find the gateway's local port, whether remote commands can be run, the file-transfer method, the idle-lock time in minutes, whether an agent may run inside the cluster, the scheduler, queue and work path, and the login limits. An item you do not know is left blank with Enter: it stays "unknown" and is never guessed. On saving, init lists the items still unknown, and choosing the same name when making a new config can ask for them again. There is no automatic re-asking later yet. A connect command that carries a known secret pattern (`password=`, `--token`, `sshpass` and the like) is refused. The check does not recognize every secret, so keep secrets out of the command and authenticate with an ssh agent or a key file. The profile is saved at `~/.labhq/sites/<name>.yaml`, or in the folder `LABHQ_SITES_DIR` names. A folder inside a repository, or under any folder holding `.git`, is refused, and on POSIX the file is readable by you alone (0600). The config keeps only the profile's name as `hpc.site_profile`. A profile with the same name is not replaced by a blank one: its values are shown as the defaults (Enter keeps the old value; yes/no questions are shown as `y`/`n` and also accept `true`/`false`). Answers you change are still saved to that file, so if another config uses the same profile, pick another name. An unreadable file is not overwritten. **Do not put a profile in a repository.** It holds hosts, ports and paths. The pre-publication check (`scripts/check_public.sh`) fails when a tracked file has the profile's first key (`labhq_site_profile`, quoted or indented too) or a `.labhq/sites/` path. Limits: it is asked only when a new config is made. An existing config is not asked: write the profile file yourself and put its name in `hpc.site_profile` (`--yes`, pipes and `--dry-run` neither ask nor save). The check does not find a copy written in flow style (`{...}`) or with anchors. It is not connected yet. The session manager and the `labhq_hpc` tool do not read this profile today, so setting `hpc.site_profile` changes no HPC behavior. The connection (#1295 stage C) will be described in the staff-tools and configuration chapters when it is merged.
`--yes` accepts defaults and `--dry-run` shows the changes and doctor checks without creating files. An existing config is preserved and replaced only with `--force`.
On Windows, init leaves out the restricted zone; if a personal Codex instruction file exists it adds a staff-only `CODEX_HOME`, and if `~/.claude` exists it adds a Claude-staff-only `CLAUDE_CONFIG_DIR` (`~/.labhq/claude-staff`), and prints the login commands a person must run.
init asks for the work folder as `runner.workspace_root` when it creates a new config. If the Windows system drive is under 128 GiB or its free space is below the warning threshold, init points to candidate fixed data drives with room. Choose a path on the drive you want yourself. `--yes` keeps the existing default path and never moves or deletes anything automatically.

If the Codex `bin` is empty or `auto`, the highest-version folder in the Windows app is chosen, and mtime is used only when versions cannot be compared. doctor prints the chosen path. Without the app, PATH is used.

**When configurations overlap (#613).** If labhq instances with different config files run on one PC, they can mix each other's records and approvals or open the wrong office. A running gateway and runner write their own *identity* at startup: the config file that started them, and fingerprints of `gateway.state_dir`, `runner.state_dir`, `runner.id` and the port (both are hashes; no secrets). The files are `labhq-gateway-owner.json` in the gateway state folder and `labhq-runner-owner.json` in the runner state folder; the gateway also returns the same hash as `identity` in `/api/health` (no paths or tokens). `doctor` (the `instance` row) and `up` compare the identity of whoever holds the state folder, runner state folder and port against the current config, and report in plain Korean with the command to fix it. They only read; the default `doctor` uses no network. `--runtime` checks the authenticated gateway state.
- Same state folder: if a process with a different identity is alive, `up` does not start and points to `labhq -c <that config> open` or `down`. If it is still running with a config that changed after this config file started it, `up` points to `down` then `up`. If it is not alive but the config that last used the folder differs, it only warns.
- Same runner state folder: two runners must not share `runner-<id>.sqlite3`, the control folder and the input hash cache, so this is blocked even when `runner.id` differs. Starting `labhq runner` or `labhq gateway` directly does the same check at startup and does not start while blocked.
- Same port: if a gateway of another config runs on this port (only when that config's process record points to that config), `up` stops and tells you which config it is and `labhq -c <that config> open`. A gateway that answers with the same token but whose `identity` differs from this config is not used, and an older gateway that does not report an identity is accepted only if this config's process record vouches for it. A gateway that is not accepted is not written to `labhq-last-config.json` or the primary config.
- Primary config: the config path of the first successful `up` is written once to `labhq-primary-config.json` in the default state folder (`~/.labhq/state`). Running `doctor` or `up` with another config warns; to change it, use `labhq -c <new config> up --make-primary`. Instances made with `--instance` are deliberately separate, so they do not become the primary config and are not compared.
`up` writes `labhq-last-config.json` in that state folder only after confirming it is its own gateway. If the config file is deleted, that record is ignored.

Before running, use `labhq doctor` to check config, engines, staff and compute tools. `labhq doctor --json` writes `capabilities.json` in the runner state directory, and connects to public data sites only when `--network` is added. The `runner_capabilities` in this manifest are facts computed from the same config and roster as what the runner reports. The `research lane` row tells you whether the research lane runs to the end. With only `research.enabled` on, it warns that the lane stops after CP1; `evidence_checkpoint` must also be on to proceed to CP2, review and report. A misspelled key under `research` is an error at startup.
doctor separates **config readiness** from **operational readiness**. Before deployment, use `doctor --runtime`. A stale or unknown PID identity of a daemon fails; a pristine or normal down is shown separately. Remote and foreground roles do not require a local PID and are verified by the authenticated gateway and runner connection (including a running WSL runner). Past up/down history with no PID record is resolved only when this authentication and connection are confirmed; a missing record without authentication, and history lookup errors, keep failing.

For an instance that uses a reviewed independent owner Job on Windows, doctor shows `contained_verified` once it confirms the four daemon generations with the operator contract pin outside state, `contained-runtime.json`, and a fresh owner challenge. It also checks the deployment path and hash of the actual inspection code. The default detached check is kept and does not erase authentication or runner connection failures. The lifetime cap of the owner receipt is `runner.contained_max_s` (default 5400 s, minimum 60, maximum 86400); for a long research run such as 15 hours, the issuing owner must use the same value (#938). It does not confirm staff children, request termination or a research GO. [Receipt and RPC contract and limits](../reference/contained-runtime.md).
The `disk` row of doctor reads the drive free space of the work folder, temp, and the Codex/Claude staff homes. If the gateway state folder (`gateway.state_dir`, SQLite and events) is on a different drive, that drive is read separately; on the same drive the row is not repeated. If the folder does not exist yet, the nearest existing parent is checked. The default warning is under 10 GiB or under 5%, adjustable with `runner.disk_warning_free_gb` and `runner.disk_warning_free_percent` (0 disables that criterion). For the work folder and gateway state folder drives, free space under `runner.disk_fail_free_gb` (default 2 GiB, the same threshold the runner uses to ask the PI before a task starts) is a fail (0 means no fail). Temp and staff-home drives stop at warn. A failed lookup is also a warn. When a step copies an earlier step's outputs to `inputs/<step>`, the runner first compares the total file size with the free space on the work drive; if the total exceeds the free space, it stops before copying any content and records, in the activity log and the staff briefing, that the input cannot be used, with the reason (size needed and free). On drives where real usage differs from file size, such as compressed volumes, this calculation is not guaranteed. The staff member asks the CSO, and the original outputs are untouched. If free space cannot be read, the copy proceeds within the existing limit as before, and if the disk fills during the copy it reports `disk full during copy`. A download that a staff member makes through a shell has an unknown size in advance, so this input-copy check does not block it, but the shell command check below looks at it separately.

**Shell download and unpack check** (#678): when a Claude staff member runs `curl`, `wget`, `unzip`, `tar`, `7z x`, `git clone`, `fasterq-dump`, `prefetch`, `aws`, `gsutil` or `rsync` through Bash, even a command the policy allows first looks at the free space of the target drive. The target folder is the one named by `-o`, `-O`, `-P`, `--output-dir`, `-d`, `-C` or the folder argument of `git clone`, otherwise the work folder. Other paths written in the same command are read too (a `curl` with several outputs, the place an earlier `cd` moved to, the target of a redirection `> file`, `>> file` or `&> file`), and if any of them is on a drive below the floor the PI is asked. The command is read the way bash reads it: `;` and `#` inside quotes are text, `#` starts a comment only at the start of a word (`url#frag` is one word), and `2>&1`-style descriptor duplication is not a file. The value of a clustered option such as `curl -dfoo -o file` separates the data value from the output option, and `curl -Lo file` and a `-d` that follows the patterns of `unzip file -x pattern -d folder` are read as well. If free space is below `runner.disk_fail_free_gb` (default 2 GiB), whatever the size, or unpacking a known size would take it below that, the PI is asked through an approval card. The size is the uncompressed total of the zip listing for `unzip`, 4 times the archive size (an estimate) for `tar` and `7z x`, and unknown for downloads and the other commands. With an unknown size nothing is blocked, and only a warning goes to the work board when free space is under the warning levels (`runner.disk_warning_free_gb`, `disk_warning_free_percent`). It never only blocks: if the PI approves, the command goes on. Commands it cannot parse (pipes, variables, substitutions) and drives it cannot read are left alone. Rules pre-approved in `--allowedTools` such as `Bash(unzip *)` or `Bash(git clone *)` are removed for staff with the approval gate so the check applies. The shell commands of a local job the runner starts itself get the same check (#1167). If a command the policy allows heads for a drive with too little space, the same approval card asks before the job starts. Free space below `runner.disk_fail_free_gb` asks even when the size is unknown; with an unknown size and space only under the warning levels, it only logs a warning. An error during the check never blocks a command the policy allows. The PowerShell tool gets the same check (#1167): `-OutFile` of `Invoke-WebRequest` and `Invoke-RestMethod` (`iwr`, `irm`, `curl`, `wget`), `Expand-Archive` (`-DestinationPath` and the uncompressed total of the zip listing) and `-Destination` of `Start-BitsTransfer`, by the same rules. It is read as PowerShell reads it, so a backslash is a path separator and text in single quotes is literal. A download or unpack whose cmdlet name is in the text but that the reader could not place, such as `$r = iwr ...` or `[void](iwr ...)`, is not passed either: the free space of the current folder's drive and of every drive named in the command (including a drive-relative path such as `D:a.zip`) is checked. If any is below the floor the PI is asked, if only under the warning levels a warning is logged, otherwise it is allowed. There is no deny. A name inside quotes or a comment can get the same check. A backtick inside a cmdlet name (`iw`r`) is ignored when counting, as PowerShell does. A network path (`\\server\share`) counts only when it is a value the command writes to (`-OutFile`, `-DestinationPath`, `-Destination`). If this PC can read its free space it is judged by the same rule as a drive; if not, only a warning is logged and nothing is blocked. A share that is only read from is not looked at. An `iwr` that the reader did place and that does not write a file, and a path with a `$` variable, are left alone (an unplaced `$r = iwr ...` gets the check above even without `-OutFile`, so a low-space card can appear for it), and a pre-approved rule such as `PowerShell(Invoke-WebRequest *)` goes through the gate too. Not covered: Codex, Gemini and cli staff (the engine sandbox runs their commands itself), PowerShell's `Copy-Item`, `robocopy` and `Invoke-Expression`, and a disk that fills during a command. A prefix rule (`Bash(ls *)`) that pre-approves a whole chain is no longer listed: Claude Code checks a chain command by command (#1163). When a task starts (#678), the runner reads free space on the work-folder drive again. Below `runner.disk_fail_free_gb` (default 2 GiB, 0 turns it off) it does not start the task and asks the PI with a **Low disk space** card. Approval starts it; if the PI declines or does not answer within 24 hours (a time limit set by the runner), it does not start and records the reason. While this card is open, the web shows the request as waiting for a PI decision. The judgment uses the free space of the drive of the work folder this run actually uses (including cases where resume or retry uses a different drive), and is made before the work folder is created or an execution slot is taken. Below the warning threshold (10 GiB / 5% above), it only logs a warning in the work-board log and proceeds. If the drive cannot be read it does not block, and the automatic environment fix (`facilities_fix`) is not subject to this check. A folder for large raw data is set with the optional `runner.bulk_data_root`. If set, the staff briefing gets one line, "Download large raw data (several GB or more) under this folder", with the free space. This folder is outside the work folder, so it gives no new write permission and writes go through the usual approval judgment. If it spans a controlled zone, it is not used in the briefing and a warning is logged. If unset, nothing changes. A configured work folder is included in the pre-publication private-path check regardless of its name. [Verification evidence](../reference/disk-preflight-752.md).

**Disk watch while a task runs** (#678): for what the earlier check cannot stop (a download of unknown size, commands that Codex, Gemini and cli staff run themselves inside the engine sandbox, a drive that fills during one command), the runner reads the free space of the work folder, the runner state folder, `runner.bulk_data_root` and the project folders the staff member may write every `runner.disk_watch_s` seconds (default 30, 0 turns it off) while the task runs. If any is below `runner.disk_fail_free_gb` (default 2 GiB), it halts that task once and keeps its session. The halted task reaches the PI as the usual `Halted · can resume` card, and the task log says the disk is below the floor. After you free space and resume, the new turn checks the disk again when it starts (below the floor it asks the PI whether to start). Set `runner.disk_watch_halt: false` to log a warning without halting. If the halt fails it is tried again at the next beat, and a drive it cannot read is skipped. A facilities fix is not watched because clearing a full work folder is its job. Limits: a task that writes more than the free space between two reads has already filled the drive (the 2 GiB floor is the cushion), and when the gateway is on another PC its database drive is not visible to the runner (doctor's gateway drive row covers it).

doctor checks only the engines the roster uses, and groups the skipped network and dry-run login checks into one line. The Claude `login` row does not stop at a passing `claude auth status`: it reads the dates in `.credentials.json` in the staff folder, and turns the row into a fail with a sign-in-again hint when the login can no longer refresh itself (the refresh token has expired, or there is no refresh token and the access token has expired) (#1276). It uses no token value and calls nothing. If status says another sign-in source is active (an API key or token), the old file is not looked at. A token revoked on the server and a login kept in the OS keychain cannot be seen this way, so they still show only at the first staff turn. If you set `runner.contract_dir`, doctor reads that folder instead of the default `agents/contract`, and matches the runner on contract validity and duplicate-ID precedence. It does not move or edit expired contracts. If there is any fail, no active staff, or any roster engine executable is missing, doctor ends with `Ready to run: no` and the reasons. Other warns do not change readiness.

`runner.facilities_support` defaults to `unspecified` (always WARN). `required` is FAIL when absent, failed, unconfirmed, dry-run or mock; `optional` is OK only for ready. init preserves an existing explicit value (including with `--force`). See the [verdict table and limits of readiness evidence](../reference/facilities-support-983.md).

`labhq doctor --canary <agent_id|all>` calls real models only when explicitly requested. It makes three calls per staff member: a short fixed answer, resume in the same session, and cancellation immediately after starting. These calls incur charges. It reports pass/fail for result, cost and token reporting (cost is unknown if the engine does not provide it), session ID, resume and cancellation, and includes them in the `--json` manifest. CI and ordinary `doctor` do not run the canary.

Cancellation passes only when Windows Job termination is verified. Missing or unverified cleanup evidence is a failure; it does not establish that a process remains. Canary runs only when Windows Job isolation and termination can be verified; on Linux and other unsupported environments it fails before calling a model. Ordinary `doctor` checks remain available. See [boundaries and remaining work](../reference/engine-canary-35.md).

npm's `.cmd`/`.bat` shims can corrupt multi-line prompts, so labhq unwraps only standard npm shims and runs them with Node.js.
Shims it cannot unwrap are refused. To specify one directly on Windows, use `engines.<engine>.bin` and `prefix_args` (check the installed package path).

For Codex staff login isolation, follow the dedicated `CODEX_HOME` note in [Known limits](17-known-limits.en.md#known-limits). `labhq doctor` checks the setup.

### Analyzing in this PC's WSL

Choose the Windows config and run `labhq -c <config> setup-wsl --check` to check tools, plugin and runner connection. Analysis readiness needs all of: the bioinfo manifest, the bioinfo-analyze skill, Java, Nextflow, the WSL Claude CLI, and the staff account login. Only a WSL confirmed ready at connection and roster refresh gets priority assignment; if not ready, native is used.

On an installation without WSL configured, `doctor` prints only a line saying the optional feature is off. After you run `setup-wsl --check` yourself or enable WSL, it reports each readiness item and the real WSL staff login path.

1. Start the gateway with `labhq -c <config> up`.
2. `labhq -c <config> setup-wsl` prepares the missing Nextflow (24.10.5), editable labhq venv and runner config. It saves enablement only after confirming analysis readiness and the connection. It only gives guidance for Claude CLI installation and login and for administrator commands.
3. After that, `up` and `down` also start and stop the WSL runner. To control it separately, use `wsl-runner start` or `wsl-runner stop` with the same config. It reuses the existing supervisor and process-identity checks.

**When WSL is not ready (#612).** When work given to `bioinfo-agent` (a direct request or an already planned step) has nowhere to go and the config has `runner.wsl`, one card per request asks "WSL is not ready yet. Set it up?". A yes makes the gateway run the same preparation as `setup-wsl` in a thread. Fifteen minutes is the limit of the wait: a preparation already started cannot be stopped, and no other setup is started until it ends. If another native runner hosts the same agent (for instance, briefly disconnected), the existing wait applies and no card is shown. If commands that need administrator rights remain, the card and the error show them, and the request stops at once instead of waiting for a runner (cost $0). A no or a timeout is not asked again within the same request. If the gateway is not on the PC that has WSL, nothing runs and only `labhq setup-wsl` is suggested. The card and feed carry item names and fixed advice, never installer output.

**Running in this PC's WSL (#612).** You can pick WSL when you send a request: `labhq send --wsl`, the "In WSL" checkbox of the web request box, or `run_where: "wsl"` in the API (default `auto`). Picking it opens the card above once per request before planning reads the staff list (it asks even when another native runner also hosts the agent); on a yes it waits until the WSL runner owns the agent after the preparation, then pins that request's `bioinfo-agent` work to the WSL runner (`session_runner`). A pinned task goes only to the WSL runner even while another request's `bioinfo-agent` work is still unfinished on a native runner, and a resend or a recovery after a gateway restart goes to the same runner; if the WSL runner drops for a moment the task waits for it instead of running natively. A native runner that tries to take the work is refused at no cost. The wait for the WSL runner is at most 5 minutes, and if `runner.wsl` is not configured, the check or setup fails, or there is a no or a timeout, nothing is waited for: the reason is left in the request's `run_where_note` and the request goes on without WSL. Planning is told "the PI chose to run in this PC's WSL" only for a request that actually got WSL; one that chose it but goes on without it is told the `run_where_note` reason and "runs without WSL" instead, so the plan does not assume WSL. A CP1 revise request and follow-ups keep the same choice. The choice applies to `bioinfo-agent` only, so adding it to a request addressed to another staff member is refused (400 in the API, an error in the CLI and the web box). See the whole-request HPC/local choice below.

| `runner.wsl` setting | Default / purpose |
|---|---|
| `distro`, `user` | `Ubuntu-22.04`, the distro's default user |
| `id` | `lab-wsl` — if it equals the Windows runner's at activation, config and start are refused |
| `bioinfo_agent` | `/mnt/d/bioinfo-agent` |
| `root` | `.local/share/labhq/wsl-<config hash>` in the Linux home; separates venv, state, logs and staff config |
| `gateway_url` | the existing address → the Windows NAT address if localhost fails. Default ports ws 80, wss 443 |
| `enabled` | true when setup's connection check succeeds |

The token is passed over stdin and kept in a 600 config file inside a 700 folder on Linux. It is not stored on the Windows mount. If NAT cannot connect, bind the gateway to an address reachable from WSL and check the firewall. Setup does not change the bind or the firewall.

Work uses the same `/mnt/<drive>/…` folder as the Windows `runner.workspace_root`. Regardless of where the gateway is, work, result and event paths are converted through the target runner's `runtime_env`, joining project, reference, `inputs/<step>`, manifest and bundle. `/home` work folders and UNC paths are refused. Setup copies the Windows approval and budget policy and the reference roots (including projects), and also converts personal and controlled-zone paths. A conversion failure is a config refusal; if you changed the policy or reference roots, run `wsl-runner stop` and then setup again.

Each staff member has exactly one responsible runner. If a task is running or its delivery result is uncertain, the assignment is kept and new tasks go to that runner too. When everything is finished, bioinfo-agent prefers the ready WSL, and falls back to the connected Windows staff if WSL is disconnected. If only the WSL start fails in `up`, it prints one warning line and the native start still completes as a success. The CSO reflects the connected runner's Nextflow and Docker checks in the plan. The WSL Claude CLI and staff login (`root/claude-staff`) are prepared separately; setup does not log in.

### Running a whole request on HPC or this PC

An online runner with a built-in scheduler, HPC tools and an eligible processing worker prompts for the run location after briefing and before CP1 (#578). A direct request checks only its named staff member. Without an eligible worker, local is selected without asking; an unanswered prompt starts no processing steps. CLI answers are `labhq approve <id> --note "1: a"` (HPC) or `"1: b"` (this PC).

| Choice | Execution and data location | Time and cost |
|---|---|---|
| HPC | Download, preparation, QC, analysis and figure/report-file generation all run as HPC jobs | Queue waits and possible server charges |
| This PC | Every processing step is local; HPC job submission is blocked | Uses PC resources without queue waits |

- The choice stays in the request record, CP1 card and report appendix across restarts. Mixed HPC/local plans and HPC plans using another runner are refused. WSL follows the request-specific runner pinning above.
- HPC originals are separated under `hpc/<request>/steps/<step>/`. Jobs run in that step's `outputs/`; prior-step inputs are read only from hash-verified `data/<producer>/<source-task>/` copies. The request bundle is created separately.
- Staff prepare and submit scripts and read permitted summaries only. Completing an HPC step requires a submission record. Operators prepare parent-folder access for shared accounts (`submit_prefix`); input-link restrictions remain.
- Existing project/path-reference inputs and runner environment bindings are refused on HPC because scheduler-readable snapshots are unavailable. Stored precedent texts are read by the CSO plan and local steps only and are not attached to HPC steps, so they no longer refuse an HPC request (#1336). Staff with configured project inputs, or only an external HPC MCP, are ineligible for whole-request HPC.

These are plan and submission checks, not a sandbox for the entire CLI. Real HPC, account switching and OS isolation are UNVERIFIED. [Structure](08-structure.en.md) · [Verification evidence](../reference/hpc-step-workspaces-578.md).
