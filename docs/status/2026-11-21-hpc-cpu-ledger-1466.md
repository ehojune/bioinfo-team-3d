## 결론

Slurm 사이트 프로필의 선택 항목 `max_concurrent_cpus`를 runner와 init 시험 잡에 적용했습니다. `pinned_nodes`를 비우면 노드는 Slurm이 고릅니다.

## 바뀐 것

- 같은 runner 상태 DB와 사이트 프로필 이름을 쓰는 두 경로가 SQLite에서 제출 전에 CPU를 예약합니다. 실행·대기·접수 미확정 잡을 합산합니다.
- 이전 runner 제출은 잡 ID·이름·제출 시각으로 대조합니다. 새 잡에는 고유 Slurm 이름을 붙여 응답이 끊겨도 같은 작업을 다시 보내지 않습니다. ID를 찾으면 원래 스크립트와 결과 경로를 돌려줍니다.
- 상한을 켠 Slurm 제출은 1노드·1태스크의 Bash 잡으로 제한합니다. 큐와 accounting에서 접수나 종료를 확인하지 못하면 예약을 유지합니다. [squeue](https://slurm.schedmd.com/squeue.html) · [sacct](https://slurm.schedmd.com/sacct.html)

- CPU 원장 테스트를 Windows 경계 목록에 넣었습니다. 한영 설정 매뉴얼에 상한 설정과 첫 현장 점검을 추가했습니다.
- `submission_id`로 의도적인 반복 실행을 구분합니다. 같은 ID의 재시도에는 기존 잡을 돌려주고, ID를 재사용하면서 설정을 바꾸면 거부합니다. Slurm이 `REVOKED`로 보고한 잡의 CPU를 반환합니다.

## 실행한 것

- 배포 venv에서 관련 테스트 622 passed, 27 skipped. 가짜 Slurm으로 60 허용·61 거부, 병렬 호출, 다른 세션·사이트 제외, 기존 잡 합산, 응답 유실 뒤 복원과 두 제출 경로를 확인했습니다.
- Windows 경계 목록 검증과 CPU 원장 테스트 17건, 공개 저장소 검사를 통과했습니다.
- 리뷰 수정 뒤 배포 venv에서 관련 회귀 247 passed, 2 skipped. MCP에서 같은 설정의 별도 실행과 기존 잡 재조회, 응답 유실 뒤 재시도, 예약 해제를 확인했습니다.

## 남은 일

- 첫 현장 제출 전, 로컬 사이트 프로필에 `pinned_nodes: []`와 `max_concurrent_cpus: 60`을 적용하고 실제 실행·대기 잡과 할당 CPU를 대조합니다. 현장 접속·제출은 미검증입니다.
