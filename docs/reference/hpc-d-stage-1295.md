# HPC D단계(#1295): 실제 사이트에 한 번 접속해 읽기 전용으로 확인

사이트의 호스트·사용자·경로·제품 이름과 계정 이름, 포트 번호는 적지 않습니다. 원문 로그는 작업자의 로컬 폴더에만 있습니다.

| 시도 | 일시 | 결과 |
|---|---|---|
| 1차 | 2026-11-07 | 접속이 셸 단계 전에 끊겨 명령을 하나도 실행하지 못했습니다(첫 시도와 재접속 1회, 로그인 2회). 원인은 2차 로그로 밝혀졌습니다. |
| 2차 | 2026-11-07 | 같은 방식으로 끊겼습니다(시도 2회, 명령 0개). 이번에는 진단 로그로 게이트웨이의 거절 사유를 확인했습니다. |
| 3차 | 2026-11-09 | **성공.** 로그인 1회(재접속 0회)로 지시한 명령을 모두 실행했습니다(전부 exit 0). |

1·2차의 로그인 카운터는 11-07에 4/30이었습니다. 그때는 명령이 한 번도 실행되지 않았고 원격에 아무것도 쓰지 않았습니다.

## 3차 결과 (2026-11-09, PI 승인: 게이트웨이 클라이언트 로그 읽기)
- **1·2차 원인 정정**: 연결 중계기는 다른 사람의 세션이 아니었습니다. PI의 포털 계정이 연 파일 전송 창이 맞았고, **그 창의 원격 시스템 계정이 프로필의 사용자 이름과 달랐습니다.** 게이트웨이는 창을 열 때 고른 계정 이름으로만 접속을 받습니다. 아래 "원인" 절의 "다른 계정의 세션"은 이 사실을 몰랐을 때의 해석입니다.
- 확인 방법(접속 없이 로컬에서): 게이트웨이 클라이언트 로그의 장비 접속 기록에서 포털 사용자·원격 시스템 계정·창 종류(파일 전송)와 중계기 프로세스 번호를 읽고, 그 프로세스가 LISTENING 중인 로컬 포트를 OS에서 확인해 대조했습니다. 로컬 프로필의 사용자 이름을 그 계정으로 고쳤습니다(저장소 밖).
- 실행: `hostname`·`whoami`·`pwd -P`·`ls`, 도구 확인(`command -v`, scheduler는 Slurm), `squeue -u`(잡 0개), `sinfo`(PI가 말한 partition 확인), PI 지정 scratch 경로 확인, 작업 폴더 만들기, 파일 1개 쓰기·읽기·지우기(남은 파일 0개), 70초 heartbeat 뒤 명령 다시 실행. 잡 제출 없음.
- 로그인: 1회. 세션을 닫았고 접속 전후 ssh 프로세스 목록이 같습니다. 직전 로그인은 약 100분 전이어서 "어느 60분 동안에도 2회 이내" 규칙을 지켰습니다.
- 확인한 것: 첫 출력 대기 뒤 셸이 열림, sentinel로 종료 코드 수신, heartbeat 뒤 세션 유지, 접속 1회가 카운터에 1회로 기록됨.
- 발견: 대화형 셸의 bracketed-paste 제어 문자와 프롬프트 조각이 명령 출력에 섞입니다. 출력이 짧은 명령은 이 조각이 결과처럼 읽힐 수 있습니다(`hpc_session`, #1332 범위).

## 원인 (1·2차, 3차에서 정정)
- 접속한 로컬 터널 포트의 연결 중계기가 **이 PC의 다른 계정이 연 게이트웨이 세션**에 묶여 있었습니다. 게이트웨이가 "사용자 변경 불가"로 접속을 끊었고, 그 세션이나 데이터에는 접근하지 못했습니다.
- 1차에서 추정한 "게이트웨이가 로그인 처리 중에 들어온 입력에 접속을 끊는다"는 맞지 않았습니다. 같은 사유가 1차에도 있었던 것으로 보입니다(그때는 원문을 남기지 않았습니다).
- 게이트웨이 skill의 `status`가 내는 "OK: ssh can connect on port N"은 **포트가 열려 있다**는 뜻이고, 그 포트가 내 계정의 세션이라는 뜻이 아닙니다. 접속 전에 확인한 것은 포트의 LISTENING뿐이었습니다.
- 이 PC에는 여러 계정이 같은 게이트웨이 클라이언트를 씁니다. 다른 계정의 프로세스와 세션은 건드리지 않습니다.

## 이번에 고친 것(병합됨)
- 접속이 실패하면 받은 원문을 로컬 진단 폴더(`LABHQ_HPC_DIAG_DIR`)에만 남기게 했습니다. 이 로그가 원인을 알려 주었습니다. 오류 문장과 피드에는 싣지 않습니다.
- 첫 출력(배너·프롬프트)을 기다린 뒤 첫 명령을 보냅니다. 이 실패의 원인은 아니었지만 로그인 처리가 느린 게이트웨이를 위한 대비입니다.
- 프로필 검사가 `remote_exec: false`와 scheduler를 모순으로 보던 것을 접속 명령이 있으면 모순으로 보지 않게 고쳤습니다.

## 접속 전에 확인할 것 (3차부터 이 순서)
1. 게이트웨이 클라이언트 로그로 창을 연 포털 사용자, 원격 시스템 계정, 창의 중계기 프로세스를 확인하고, 그 프로세스가 LISTENING 중인 포트를 OS에서 대조합니다. 열려 있는 포트를 그냥 쓰지 않습니다. 이 방법은 사이트 프로필의 `port_owner_check`에 적어 둡니다.
2. 프로필의 포트(`-p`)와 사용자 이름을 그 값으로 고칩니다.
3. 읽기 전용 명령만 실행하고, 재접속은 최대 1회, 실패하면 멈추고 보고합니다.
4. 접속 직전과 직후의 프로세스 목록을 비교해 내 프로세스가 남지 않았는지 확인합니다. 다른 계정의 프로세스는 건드리지 않습니다.

## 확인하지 못한 것
실제 사이트에서 오류 메시지의 사이트 정보 가림(3차에 오류가 나지 않았습니다), 잡 제출·회수, 여러 직원 단계가 세션 하나를 함께 쓰는 동작(#1332)은 확인하지 못했습니다.
